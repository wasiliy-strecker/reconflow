# GPU benchmarks

ReconFlow hosts the UI, control API, queue, database and reports. Vast.ai hosts the
single rented GPU. The module does not create AWS GPU instances or another database.
All deployment resources remain in Stockholm. Development defaults to **disabled**
paid execution; local tests never contact Vast or download model weights.

## Current implementation and acceptance boundary

- Public visitors select synthetic fixtures and one allowlisted Gemma model. Standard
  suites run one excluded warmup plus three rounds of five prompts. Live sessions accept
  individual fixtures or a sequence of up to five. Free text requires operator login.
- Results are measured by the runner, not generated by the application. The comparison
  starts empty. Browser/SDK fixtures exist only in tests, not in production data.
- Local automated verification covers transport, accounting, lifecycle, API and UI.
  Hardware/CUDA compatibility, the complete Ollama download/bootstrap, actual Vast
  billing and end-to-end AWS callbacks still require the explicit live acceptance below.
- The AWS login expired during planning. No Vast key or operator secret was configured
  during implementation. No AWS deployment, GPU rental or publication has occurred.

## Limits and accounting

Defaults: EUR 10 per Berlin calendar month, EUR 1 per rental, one active rental globally,
30 minutes maximum including startup, 10 minutes startup, 5 minutes ready/idle, 120 seconds
per prompt, and 20 live requests per rental. Anonymous visitors get one rental per demo
session and two starts per source IP per day. Network addresses are stored as keyed
hashes. Expired rate-limit rows are removed during session cleanup. Proxy/NAT sharing can
cause visitors to share the IP allowance; the global ledger is the actual spending gate.

Prices are decoded and calculated as Decimal. Offer estimates include the requested
30 GB disk allocation through Vast's `dph_total`, 25 GB download / 1 GB upload allowances,
two minutes of shutdown margin and a configurable conservative USD/EUR multiplier (1.10).
Offers with missing prices, changed quotes or an estimate over the allowance are rejected.
Those traffic allowances are planning bounds for the fixed artifacts/models, not a
provider-side network spending cap.

The **full EUR 1 reservation is debited after any attempted rental**, even if the displayed
estimate is lower. This deliberately limits this release to at most ten such rentals per
month until actual provider billing reconciliation is added. The UI never calls that debit
an actual provider charge. Failures before a rental attempt refund the reservation.
Unknown creates are not automatically retried or refunded. No automatic top-ups exist.

Destroying, not stopping, ends ongoing storage billing. Deletion confirmation needs three
separate inventory observations at least 55 seconds apart. The concurrency slot remains
occupied until then. Provider outages can prolong charges; neither AWS alerts nor this
ledger promise an absolute external spending cap. Vast costs are separate from AWS credits
and ReconFlow's OpenAI budget.

## Deployment preparation

These steps prepare the existing stack; execute uploads, secret creation and deployment
only after that action is authorized. Do not enable Paid/Advanced features automatically.

1. Renew `aws login --profile portfolio`. Follow `AWS_RUNBOOK.md` to recheck the active
   Free Plan, remaining credits, project identity and Stockholm restrictions. Confirm
   EventBridge Scheduler and the additional least-privilege roles can be deployed.
2. Store a dedicated Vast key in the server-side `reconflow/vast` Secrets Manager secret.
   Allow offer reads, instance inventory, instance creation and destruction; exclude unrelated
   payment/account administration where the provider permits. Store an independent random
   operator password of at least 32 characters in `reconflow/gpu-operator`. Use private
   operator tooling or the AWS console; never put values into Terraform, Git or browser code.
3. Build the deterministic small runner package, using a new output filename each time:

   ```bash
   uv run python scripts/package_gpu_runner.py artifacts/private/gpu-runner-release.zip
   ```

   Record its printed SHA-256. The package contains only bootstrap code, the standalone
   runner and public version pins. Upload it to the **existing private documents bucket**
   under `benchmarks/artifacts/<sha256>.zip` with AES256 server-side encryption. Do not
   overwrite a released artifact. The worker issues a ten-minute presigned GET URL.
4. Set `vast_secret_arn`, optional `gpu_operator_secret_arn`, `gpu_runner_artifact_key` and
   `gpu_runner_artifact_sha256` in ignored operator Terraform configuration. Keep
   `enable_gpu_benchmarks = false` during deployment and verification.
5. Build the backend image from `requirements.lock` and deploy it through the existing
   ECR/Lambda workflow after authorization. Terraform adds a fourth entrypoint,
   `reconflow-gpu_watchdog`, and its minute schedule. Run versioned SQL migrations before
   API/worker rollout. The manual deployment workflow now updates the watchdog too.
6. Verify the watchdog succeeds, its private `benchmarks/watchdog.json` is fresh, no
   unexpected provider instances exist and the frontend/API expose the disabled module.
   Only then enable admission through the same stack. Activation checks require deployed
   HTTPS and actual S3; Moto/loopback configurations cannot rent a GPU.

The default runner image is the official amd64 Python 3.14 slim image pinned in config and
Terraform. It has no application credentials and requests NVIDIA compute/utility devices
from Vast. Ollama 0.40.16 is downloaded over TLS and verified against the release asset's
SHA-256. The pinned Gemma tags are checked against registry manifest digests both before
and after download. Updating any of these requires a reviewed new runner artifact and
revalidation; do not silently update tags. The repository's Python backend remains 3.12.

Official references: [Vast Python SDK](https://docs.vast.ai/sdk/python/reference/create-instance),
[Vast pricing](https://docs.vast.ai/guides/instances/pricing),
[Ollama generation API](https://docs.ollama.com/api/generate),
[Ollama release](https://github.com/ollama/ollama/releases/tag/v0.40.16),
[Gemma tags](https://ollama.com/library/gemma3/tags).

## Measurement interpretation

The runner measures TTFT from immediately before its localhost inference request to the
first nonempty response chunk. Response duration ends at the completed stream. Both use
monotonic time and exclude browser polling/network latency. Progress callbacks run in a
separate thread. Tokens/s uses actual `eval_count / eval_duration`; it is never estimated
from characters. Ollama durations, prompt counters and available cache counters are retained.
Initial model download/load times are separate metadata. Runtime bootstrap/image-download
time is not presented as model inference performance.

VRAM and GPU utilization are sampled every 200 ms using NVIDIA telemetry; these are sampled
peaks, not guaranteed instantaneous maxima. Missing telemetry is null. Ollama's loaded model
memory identifies CPU offloading. Such results are clearly marked and should not be read as
pure GPU comparisons. Repeated prompts may benefit from caching: this protocol does not
claim cold KV caches. Compare matching protocol, model digest, quantization, context and
runtime, and inspect the full report before drawing conclusions from small sample counts.

Public completed standard reports remain in Aurora and `benchmarks/reports/`; the existing
`sessions/` S3 expiration does not affect them. Private prompt/output content is never put
in public reports and is scrubbed on session deletion/expiry cleanup. Do not submit private
documents or customer data to marketplace hosts. Operator text outputs are rendered as
plain text, never executable HTML.

## Live acceptance

After the deployment and paid-test action are authorized and credentials are present:

1. Select an available affordable single GPU and Gemma 3 4B. Check the offer, reservation,
   startup, first-token and completion states using the real public UI.
2. Confirm the report contains the real GPU, driver/runtime versions, pinned model digest,
   actual token counters and timing samples. Confirm S3 and Aurora retain the report.
3. Confirm the provider reports the instance destroyed and the UI confirms release. Inspect
   the actual provider bill separately from the application's conservative budget debit.
4. Run the identical protocol on a second GPU sequentially. Choose the RTX 5060 Ti 16 GB
   only if actually offered; unavailable hardware must stay unavailable. Compare both runs.
5. In a separate bounded live session test a fixture series, operator-only free text, manual
   stop and browser-close idle cleanup. Exercise a controlled runner failure and confirm
   cleanup. Never replay an ambiguous create to manufacture a successful acceptance.

Do not mark the feature hardware-validated or populate showcase numbers until these checks
have actual evidence. Save only non-sensitive real reports and timestamps when recording
the acceptance in the changelog.

## Operations and rollback

- Turning `enable_gpu_benchmarks` off blocks new rentals; it intentionally leaves the
  watchdog and existing cleanup active. UI stop remains available while admission is off.
- On `gpu.create_unknown`, inspect provider inventory by the signed `rfb1:` label. Do not
  repeat create. The application retains its reservation and reconciles automatically.
- On `gpu.watchdog_failed` / `gpu.destroy_unconfirmed`, inspect CloudWatch, the shared DLQ
  and the provider console. A stale/failed watchdog heartbeat blocks new rentals. A runner
  process exiting is not confirmation that rental billing stopped.
- Do not rotate the session signing secret or remove Vast credentials while any rental is
  unresolved. Do not remove the scheduler or roll back to an image lacking the reaper until
  every owned provider instance is confirmed gone. Keep additive database migrations.
- The local optional `docker compose --profile gpu` watchdog is for controlled development
  after configuration; it does not bypass the production activation requirements.

## Verification

Run focused GPU tests against isolated local PostgreSQL/Moto, then repository checks:

```bash
uv run pytest tests/test_benchmarks.py tests/test_gpu_lifecycle.py
uv run ruff check backend tests scripts
uv run ruff format --check backend tests scripts
npm --prefix frontend run check
npm --prefix frontend run build
terraform -chdir=infra/app validate
terraform -chdir=infra/app test
```

`frontend/e2e/benchmarks.spec.ts` covers the honest disabled/empty state, mobile layout,
idempotent rental submission and cleanup controls. Its enabled rental scenario is an
explicit browser-only contract fixture. The existing invoice browser test remains required.
Use `RECONFLOW_API_URL` for a separate Vite test API and `DEMO_URL` for Playwright.
